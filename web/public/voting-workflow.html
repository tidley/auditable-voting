Voting workflow and tutorials

The shipped questionnaire flow: admission, blind credentials, anonymous answers, release and verification.

Start demo — isolated offline sandbox. Fictional roles, no live publishing, stored election data or connections. Only the saved light/dark preference is shared with the live app. Reset/reload repeats the same election. Runs offline after assets load; cold offline access needs a locally served build. The tutorials below describe the real app: normal publish/submit controls create real records. Use fictional data for a live rehearsal.

1. End-to-end flow

  1. Organiser: prepare questions and eligibility → publish the signed definition.
  2. Admission branch: general/private invitation or paper code + master-list number. Paper inputs derive a combined election/number/code hash locally.
  3. Configured issuer: browser or Linux worker checks election window, eligibility, scope and admission state. Invalid/pending requests need correction or approval; valid requests receive a blind signature.
  4. Voter: unblind credentials locally → answer visible applicable questions → submit.
  5. Publication branch:
    • Valid signed private-worker route and matching queue/release delegation: encrypted ballot → worker validates and persists → encrypted Queued privately receipt → threshold/deadline → shuffled public batch.
    • No valid private route: normal public ballot publication. This is the current fallback, not private batching.
  6. Observer: verify proofs, scopes, answers and uniqueness → check public tally and final results.

Do not assume timing privacy merely because a worker is configured. Inspect the signed definition and matching private-queue and batch-release capabilities before a real election.

3. Who can see what?

  • Organiser / issuer: eligibility, admission hashes and identity-bound issuance/recovery records. Paper code and number are not in the anonymous ballot.
  • Private ballot worker: arrival metadata and payloads it handles; reports aggregate queue progress rather than voter-linked decisions.
  • Relays: public records, encrypted envelopes and network/timing metadata.
  • Observer: released responses, proofs and results. Encrypted answers require the appropriate key.
  • Voter: their identities, admission inputs, credentials, answers and recovery state.

Blind issuance separates eligibility from the anonymous response. It does not prevent timing correlation, coercion or device compromise. An operator running issuer and ballot worker has both roles' visibility.

4. Organiser tutorial

  1. Open Organiser. For rehearsals use test identities; for real operation retain encrypted backups.
  2. Create questions, opening/closing times, groups, required questions and conditional follow-ups. English is the base; French/Tamil are optional. Paper output is English.
  3. Choose browser issuance or the delegated Linux worker. Keep the issuer online and deliver the worker's private configuration before use.
  4. Choose general/private invites or paper codes. For private batching, set the signed worker identity, DM relay allowlist, threshold and deadline with queue/release delegation before publishing. Do not add these to an immutable published definition.
  5. Publish and open/select the questionnaire in Organiser so its issuer runtime is available. Under Session → Results & Voters (Voters), find Paper ballot access. Enter master-list numbers and a future expiry; generate and print the Crockford codes. Treat printouts as sensitive bearer material.
  6. Only the combined election/number/code hash and lifecycle metadata persist. No separate roster mapping is stored. Do not regenerate for the same roster after reload: earlier codes cannot automatically be found/revoked and both may remain usable. Duplicate checks cover only the open print session.
  7. Test receipts and batch release in a separate rehearsal election before using the configuration for real voters. Share invites only once the issuer is ready. Separate credential delivery from aggregate queue progress. General requests may need approval; valid paper requests issue without another manual approval.
  8. Allow final batch release to finish, then close and publish results through the organiser controls. Paper rounds use organiser-controlled closure, not automatic expected-count completion.
  9. Have an independent Observer verify the result.

5. Voter tutorial

  1. Open your questionnaire invite. For paper access, enter the printed code and master-list number on Vote. They derive the admission hash locally and never enter the anonymous response.
  2. Send the request and wait for credentials. Correct a mistyped paper request while pending. An admitted code binds to that voter identity, not another identity. Retain browser state or an encrypted backup.
  3. Select a language if needed. Answer applicable questions only; required visible questions must be complete. Follow printed answer/leave-blank instructions.
  4. Submit. With private batching, wait for the authenticated Queued privately receipt. Read any rejection reason; sending a DM alone does not mean acceptance.
  5. Keep submission details. Wait for batch release before expecting a public row. Do not create another identity merely because release is delayed.
  6. Check release and final results in Observer. Ballot details in Settings helps diagnose requests/receipts.

6. Observer tutorial

  1. Open Observer and find the signed questionnaire by ID/organiser.
  2. Check the definition, issuer authority and private-release policy. No public row before batch release need not indicate a failure.
  3. Inspect Submitted Votes: proofs, scopes, conditional answers, duplicates/nullifiers and rejection reasons. Paper codes/numbers must not appear in response payloads.
  4. Aggregate batch records contain batch ID, reason and count, not a voter mapping. Observer does not display them yet. Inspecting them requires an external Nostr relay/event inspection tool and the worker's public records; it is a technical audit task, not an Observer control.
  5. Recompute and compare the final tally. Report missing/inconsistent evidence; a private receipt alone is not public proof of inclusion.

7. Protocol sequences

Admission and credential issuance

Organiser → issuer: private configuration with combined admission hashes
Organiser → voter: paper code + number + expiry + instructions
Voter → voter: derive admission hash; blind fresh credential request
Voter → issuer: encrypted request, admission hash and request identity
Issuer: check election window, scope, expiry and admission state
  invalid / bound elsewhere → refuse
  valid → persist redemption binding and recoverable issuance state
Issuer → voter: encrypted blind signature / credential bundle
Voter: unblind locally; retain credentials and recovery state

Private ballot batching

Voter → pinned worker: encrypted ballot on signed DM relays
Worker: validate; persist accepted queue entry
Worker → voter: encrypted receipt
Worker → organiser: encrypted aggregate progress
  No public ballot before threshold or deadline
Worker: fix batch membership; shuffle; persist exact signed events
Worker → public relays: fresh ballots with common release time
Worker → public relays: aggregate batch record
Worker → organiser: updated aggregate progress
Observer: independently verify and tally

Retry and recovery

Voter → issuer/worker: retry the same request after lost response
Issuer/worker → durable state: look up existing request/result
Issuer/worker → voter: replay result, not another credential
Restored voter: resume receipt listening with the response key
Restarted worker: load prepared signed public event
Worker → relay: retry identical event with the same event ID
Worker: persist completion; retry failed entries only

Retries may send the same event more than once; stable event IDs support relay deduplication. Lost issuer state, keys or voter recovery secrets require the election's recovery procedure, not an extra vote.

8. Planned, not shipped as a complete admission service

  • Signed reusable admission grants scoped to group, issuer, voter and expiry are future work. Elections still need fresh credentials.
  • Resident imports and OTP previews are not cross-device authentication. Proposed automated email delivery is not merged; an OTP UI flag is not protocol admission.
  • SMS integration is not implemented. Worker/Nostr connectivity is separate from SMS/email delivery.
